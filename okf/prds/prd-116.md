# Extending the dye rotamer library

## Why

The rotamer route needs a library entry per dye+linker. Six dyes are wanted.
Measured against `data/rotamer_library/` on 2026-08-19:

| wanted | registry name | files | state |
|---|---|---|---|
| Cy3B | `Lumiprobe Cy3b C2R` → `Cy3b_C2R` | pdb + 3 bcif + 3 weights | **ships** |
| ATTO 488 | `ATTO 488 C3R` → `T48_C3R` | pdb + 3 bcif + 3 weights | **ships** |
| Alexa 647 | `AlexaFluor 647 C2R` / `L1R` → `A64_C2R`, `A64_L1R` | both complete | **ships** |
| Cy3 | `Lumiprobe Cy3 C2R` → `Cy3_C2R_HandyFRET` | **none** | declared, no data |
| sulfoCy5 | `Lumiprobe Cy5 C2R` → `Cy5_C2R_HandyFRET` | **none** | declared, no data — *and* sulfo-Cy5 is not Cy5 |
| ATTO 647N | — | — | **absent from the registry entirely** |

Three further facts fall out of the same check, and each is a defect in its own
right:

* **`Cy3_C2R` and `Cy5_C2R` are declared but empty.** `libraries.json` names
  them with a `_HandyFRET` filename; no `.pdb`, no `.bcif`, no weights ship.
  A user asking for `Lumiprobe Cy3 C2R` gets a file-not-found from inside the
  loader rather than "that library is not available", which is the difference
  between a missing feature and a broken one.
* **`C3N_C2R` ships and is undeclared.** A complete entry — pdb, three cutoffs,
  three weight files — that `libraries.json` does not name, so nothing can ask
  for it. 97 atoms, residue names `C3N` + `C2R`.
* **`Clusters_populations.csv` is wrong and unread.** 56 of its 93
  `(library, cutoff)` rows disagree with the number of weights actually
  shipped, in both directions (`A48_C1R_cutoff30`: table 32, file 33;
  `A35_L1R_cutoff20`: table 516, file 520). Nothing in `pyext/src`, the tests,
  the examples or `../chisurf` reads it. It is a stale artefact of the upstream
  build being shipped as if it were data.

## What a library entry is

Established by reading the shipped ones, not from documentation:

| part | example | content |
|---|---|---|
| topology | `A48_C1R.pdb` | one conformer, atom names and residue names — `A48` for the dye, `C1R` for the linker; the split drives `representation/rotamer.py:711` |
| conformers | `A48_C1R_cutoff{10,20,30}.bcif` | the ensemble, one frame per cluster representative, in the BinaryCIF `_atom_site` form PRD-113 moved to |
| weights | `A48_C1R_cutoff{N}_weights.txt` | one raw cluster population per conformer, one per line, `%.18e` |
| registry | `libraries.json` | `author`, `citation`, `licence`, `filename` (the *cutoff30* stem by convention), `mu` and `r` as MDAnalysis-style atom selections for the transition dipole and its reference point, `positive`/`negative` charge selections |

The three cutoffs are three clusterings of one trajectory, not three
trajectories: for `A48_C1R` they are 711, 123 and 33 conformers. The number in
the name is the leader-clustering RMSD threshold; **the units are not recorded
anywhere in this repository** and must be pinned before anything is generated,
because a generated library at the wrong threshold is indistinguishable from a
correct one until it is used.

## Provenance, and why generated entries are not the same kind of thing

Every shipped entry carries `author: D Montepietra, G Tesei, JM Martins,
MBA Kunze, RB Best, K Lindorff-Larsen`, `citation:
10.1038/s42003-024-05910-6`, `licence: GPLv3`. They are FRETpredict's, produced
by that group's protocol, and `test/references/cgdye_fretpredict_pins.json`
pins this repository's rotamer route against FRETpredict's own numbers on them.

An entry generated here is a different object with the same file layout. It
must say so in `author`/`citation`/`licence`, and the FRETpredict parity pins
must **not** be extended over it — there is nothing upstream to be at parity
with. This is the single most important thing for the PRD to get right: the
directory would otherwise come to hold two kinds of entry that look identical
and mean different things.

## What already exists to build with

| piece | where | what it does |
|---|---|---|
| `LangevinDyeSampler` | `cgdye/sampling.py:339` | IMP Langevin/Brownian dynamics on the dye force field, protein as soft-sphere obstacles, anchor fixed |
| `LinkerSampler`, `generate_linker_rotamers` | `cgdye/sampling.py:516,682` | torsion-space Metropolis over the linker, then leader clustering — already returns a clustered library with transitions |
| `cluster_frames_leader` | `cgdye/sampling.py:48` | the leader clustering, RMSD without alignment |
| `rotamer_transition_matrix`, `rotamer_correlation_times` | `cgdye/sampling.py:102,121` | the kinetics FRETpredict's libraries do not carry |
| `bin/imp_bff_traj2bcif` | `bin/` | writes the conformer file in exactly the shipped format |
| `DyeForceFieldSystem` + `build_dye_protein_system` | C++ / `cgdye/topology.py` | the force field a dye is propagated on |

So the sampling and the file writing both exist. What does not exist is
anything that produces the *entry* — the four parts together, registered — and
no library in this repository has ever been generated.

## Blocked on

**[`impropers_are_dropped.md`](../validation/impropers_are_dropped.md).**
`build_dye_protein_system` hard-codes `impropers = []`, discarding 81 improper
terms across the two shipped components. For a dye whose ring feature is marked
`rb NO, md_fixed NO` — atto655's is — those impropers are the only term keeping
the chromophore planar. Generating a rotamer library under that force field
would sample a pyramidalising chromophore and bake the result into shipped
data, where the transition dipole is *defined* by the ring geometry. This is a
hard precondition, not a caveat.

## Stages

### Stage 0 — retire CX4 and atto655 as system fixtures

Both are from another project (user, 2026-08-19). They are currently the only
combined-system fixtures: `test/cgdye/test_combined_system.py`,
`test_cgdye_integration.py`, `test_topology.py`,
`expensive_test_all_dyes_sampling.py`, the new improper gate in
`test/scoring/test_scoring.py`, plus `cgdye/cli.py` and `analysis.py` defaults.

Retiring them means replacing the fixture, not deleting the tests — the
combined-system builder needs *a* dye+protein pair to be tested on. The
replacement should be a dye already in the rotamer library, so the fixture and
the library stop being disjoint worlds.

`atto655`'s mol2 and template survive this stage as a **candidate for the dye
library** (user: "consider adding atto655 to dye library"), not as a fixture.
It is the one dye in the repository with a hand-built force-field template, so
it is the natural first generated entry — see stage 3.

### Stage 1 — make the registry honest

Independent of any generation, and worth landing on its own:

* decide `Cy3_C2R` / `Cy5_C2R`: either the data ships or the declarations go.
  A declared-but-absent entry is worse than an absent one.
* declare `C3N_C2R`, or move it out. Identify what it is first — 97 atoms,
  linker `C2R`; the name suggests a non-sulfonated Cy3, which is a claim to
  check against the atom composition rather than assume.
* delete `Clusters_populations.csv`, or regenerate it from the weights files
  and add the test that keeps it true. Nothing reads it, so the honest move is
  probably deletion.
* settle whether **sulfoCy5** is what `Lumiprobe Cy5 C2R` meant. Sulfonation
  changes charge and hydration and therefore the linker ensemble; if the user
  needs sulfo-Cy5 specifically, it is a generation target, not a naming fix.

### Stage 2 — the generation pipeline, as a prototype

In `prototypes/dye_library/` — a new directory; `prototypes/fast_label_score`
and `prototypes/quench_pinn` belong to another session and are not touched.

The pipeline is: force-field system for dye+linker → sampling → clustering at
three thresholds → the four entry parts. Two decisions it must make explicitly:

1. **Free dye or dye-on-protein.** FRETpredict's libraries are ensembles of the
   *free* dye+linker, screened against the protein at use time; that is what
   makes one library reusable across sites. `LangevinDyeSampler` is built for
   the on-protein case. Generating with obstacles present would produce a
   library that silently encodes one site's environment. The pipeline must
   sample free unless there is a stated reason not to.
2. **Which sampler.** `generate_linker_rotamers` (torsion-space Metropolis) and
   `LangevinDyeSampler` (Cartesian dynamics on the force field) are different
   ensembles. They should be compared on the same dye before one is chosen,
   because the choice is not obviously either way and it determines what the
   weights mean.

### Stage 3 — the parity bar, then the dyes

**The gate is regeneration, not plausibility.** Before any new dye:
regenerate `A48_C1R` — the entry the FRETpredict pins already cover — with the
pipeline, and compare against the shipped one. Not conformer-by-conformer,
which no stochastic method will reproduce, but on the observables the library
exists to produce: ⟨κ²⟩, the R_DA distribution, and the E_static/E_dyn1/E_dyn2
triple on the pinned structures, at a tolerance stated in advance.

A pipeline that cannot reproduce A48_C1R has no business producing ATTO 647N,
and the difference will not be visible by looking at the output.

Then, in order of what the repository can support:

1. **atto655** — has a template already; the shakedown case.
2. **ATTO 647N** — absent entirely; needs mol2 + template + parameters.
3. **Cy3**, **sulfoCy5** — needs the stage-1 naming decision first.

Each new dye needs a force-field template (`_cgdye_improper`, `_cgdye_feature`,
LJ types) built by hand, which is the real per-dye cost and is not automated by
anything here.

### Stage 4 — kinetics the shipped libraries do not carry

`rotamer_transition_matrix` and `rotamer_correlation_times` already exist and
FRETpredict's entries have nowhere to put their output. A generated entry could
carry the transition matrix and rotamer correlation time alongside the weights,
which is what a dynamic-quenching or diffusion-with-traps model needs and
currently has to assume. Additive — it does not change how existing entries
load — so it is last and separable.

## Not in scope

* Changing the rotamer route's physics or the FRETpredict pins.
* Retiring the FRETpredict libraries. They stay; generated entries sit
  alongside them, distinguishable by their registry metadata.
* Automating force-field parameterisation for arbitrary dyes.
