# PRD-121: FPS, natively — the C# FRET positioning and screening toolkit as programs in `bin/`

**Status:** phase 0 done (2026-08-31)
**Done:** The survey — what FPS is, what `IMP.bff` covers, and the **eight** things it does not. **FPS's native AV is rebuilt** and reproduces both shipped reference clouds exactly, and `IMP.bff` now matches it to **0.99 of volume at 0.121 Å** (G8 closed). Four defects fixed on the way, one of them user-facing.
**Missing:** Everything in "The gaps" except most of G8. The two that carry the PRD are **G2** error estimation (a parametric bootstrap, which `imp_bff dock-errors` is not) and **G3** screening diagnostics.
**Shipped since:** `bin/imp_bff_fps` (`score`/`dock`/`refine`/`screen`/`convert`, both input doors, worked `--help` examples), the two-body example data `examples/structure/HIV_RT/` (FPS's own docking case) and `examples/structure/fret_docking.py`. Running the example found a **segfault** — an unresolvable labelling site indexed an empty vector — and the stderr spew that had been burying every run's output.

**Next:** **Phase 0 is closed.** **G7's last item closed 2026-09-01:** the excluded-volume term has a radii source and a scale of its own (`clash_radii_source` / `clash_radii_scale`, defaults `"imp"` / 1.0), so a run can be given FPS's Bondi-scale hard sphere instead of IMP's united-atom radii. That halves of the score can now agree about how big an atom is; on HIV-RT it is a factor of **17.9** in clash energy, and it takes the G2 bootstrap off **0.000 +- 0.000 A** to 0.0689 +- 0.0155 -- non-zero, and still thirty times below the clash-free 2.13 A, so G2's pinning is only partly a radii artefact. Both A/B pins are in the suite (`test_fps_av_parity.py`, `test_fps_screening_ab.py`; [`okf/validation/fps_screening_ab.md`](../validation/fps_screening_ab.md)) and the reduced fixture is in `test/input/fps/`. Phase 1 (G3, screening diagnostics) is next. The apparent +2 Å bias turned out to be the **accessible-contact volume** (G9, closed 2026-09-01): the two implementations agree with each other to −0.31 Å / rmsd 1.20 Å with it off, and honouring the one `FRET_screening.fps.json` asks for brings this module to +0.22 Å / 0.91 Å of the published table ([`okf/validation/fps_screening_ab.md`](../validation/fps_screening_ab.md)). Was read for a day as "not in this module", on the mistaken premise that the table came from FPS. Was: Phase 0 is nearly done — the oracle, the parity measurement, one clearance derivation across both doors, the phantom weight (in **both** its copies), the empty-volume warning, and the attachment-atom drop that closed G8 (`okf/log.md`, 2026-08-31 (5) and (6)). Left: the reduced `test/input/` fixture with a parity test against the oracle, then the Zenodo T4L set.


## Why

FPS — *FRET Positioning and Screening*, Kalinin *et al.*, *Nat. Methods* **9**,
1218 (2012) — is the reference implementation of FRET-restrained rigid-body
docking and of FRET screening of a structure library. It is a C# WinForms
application with a small native C++ core
(`../chisurf/junk/fps`, `Fluorescence-Tools/fps` at `eb3489f`), it is
Windows-only in practice, and its last release is v1.1.

The physics underneath it is almost entirely in this module already — AVs,
asymmetric ±χ², rigid-body assembly, excluded volume, minimisation docking.
What is missing is not physics. It is **the product**: a project that holds a
run together, an error estimate that means what FPS's means, a screening
report with the diagnostics that make a screen readable, and the three small
tools every FPS user actually uses (AV export, distance calculator, conversion
function).

Two further reasons to port rather than depend:

1. **It does not run here.** WinForms, and the shipped macOS build is a v1.1
   wrapper of a 2012 binary.
2. **Its file formats are a decade of measurements.** `FPSIO.h` already reads
   them (`read_old_lps_txt`, `read_old_distances_txt`) — deliberately read-only,
   for the reason that header states. This PRD makes them *runnable*, not
   writable.

ChiSurf is the downstream consumer, but nothing here is ChiSurf-shaped, so the
PRD is bff-local (owner, 2026-08-31). ChiSurf will call it.


## What FPS is

Five run modes over one data model, three standalone tools, and a
project/report layer.

| | FPS piece | C# source |
|---|---|---|
| Modes | Dock, Refine, Error estimation, Sample, Screening | `SpringEngine.cs`, `Refinement.cs`, `ErrorEstimation.cs`, `MetropolisSampler.cs`, `FilterEngine.cs` |
| Tools | AV interface (`FpsGui -av`), Distance calculator, Conversion function | `AVinterface.cs`, `DistanceCalculator.cs`, `ConversionForm.cs` |
| Data | positions `.txt`, distances `.txt`, project `.bin` + `.txt`, results `.bin` | `LabelingPositions.cs`, `Distances.cs`, `ProjectData.cs`, `SimulationResult.cs` |
| Reports | PyMOL script, Overlay, OverlayStates, Rtable, chi2table, RMSD / best fit | `SaveForm.cs` |
| Kernels | AV1/AV3 grid + link search, cluster-BVH clash forces, MT19937 | `Fps.Native/av_routines.cpp`, `clash_routines.cpp` |

Two enum values are **not** functions: `AVS` (real dye structure) and `EDF`
(external density file) are spellings `LabelingPositions.cs` will parse and
that `AVEngine` never computes — it has `Calculate1R` and `Calculate3R` and
nothing else. They are not being ported, because there is nothing to port.

## Decisions taken (owner, 2026-08-31)

- **D1 — backend: IMP.** `dock_minimize` and IMP's optimisers stay; FPS's damped
  rigid-body integrator (adaptive viscosity and timestep, capped forces) is
  **not** reproduced. Consequence, stated up front: **scores are pinned,
  coordinates are not** — docked coordinates will not be bit-comparable to
  FPS output, and the A/B bar is agreement on χ² and on model distances.
- **D2 — several programs**, mirroring FPS's own structure (`Program.cs` has
  two entry points; the rest are dialogs):

  | program | replaces |
  |---|---|
  | `bin/imp_bff_fps` | `MainForm` — project, and `dock` / `refine` / `sample` / `errors` / `screen` |
  | `bin/imp_bff_fps_av` | `AVinterface` (FPS's own `-av` entry point) |
  | `bin/imp_bff_fps_distance` | `DistanceCalculator` |
  | `bin/imp_bff_fps_convert` | `ConversionForm` |
  | `bin/imp_bff_fps_export` | `SaveForm` |

  The five modes stay subcommands of one program because they share one
  project; the dialogs become programs because in FPS they already are.
- **D3 — both project formats.** Read the legacy FPS project **text export**
  (`om.Export`: `# Category` headers, `Key = value`, indented ` Field = value`
  for structs, array values on the following line — written beside the `.bin`
  every time a project is saved, so it always exists), and read/write an
  **extended `.fps.json`** carrying a `Project` section. Writing the legacy
  format is out of scope, exactly as `FPSIO.h` already argues for the other two.
- **D4 — bff-local.** This page. ChiSurf consumes it later.
- **D5 — both input doors, everywhere.** Every program accepts either the
  legacy **pair** (`--positions lps.txt --distances distances.txt`) or a single
  `--fps-json`. Reference atoms follow the same rule: the trailing `ATOM` lines
  after an LP line in the legacy file, and a new `reference_atoms` array on a
  position in fps.json (**schema 1.1 → 1.2**).

### What measuring against it found (2026-08-31)

**1. FPS's `.xyz` is a duplicate-expanded, density-weighted cloud, and its line
count is not a voxel count.** `calculate3R` returns `n += dn` — the **sum of
densities**, one per (voxel, dye radius) that fits, not the number of voxels
(`av_routines.cpp:414`). `AVEngine` sizes the point array by that sum and emits
a voxel once per radius that fits. So:

| file | lines | unique voxels | mean density |
|---|---|---|---|
| `p_1bp(D).xyz` | 5 473 | **3 187** | 1.72 |
| `p66(D).xyz` | 130 531 | **55 514** | 2.35 |

`p_1bp`'s multiplicities are 901 voxels once and 2286 twice — R₁ = 11 Å never
fits. FPS's `Dmp` is the mean of all 5 473 lines, i.e. the **density-weighted**
mean, reproduced here to the last digit. `IMP.bff` carries the same information
as unique voxels plus a weight column (`0.3333` = one radius of three). Same
content, different packing — and comparing one against the other is what made
the first two passes of this measurement read as a 2× disagreement.

**2. Parity is good.** `p_1bp`, L = 8.5, W = 4.5, R = 11/3/1.5, dg = 0.6,
clearance 3.0, against FPS's 3187 voxels and `Dmp (62.141, 47.425, 101.432)`:

| bff configuration | voxels | vs FPS | \|Δmean\| |
|---|---|---|---|
| heavy atoms, IMP united-atom radii | 2 816 | 0.88 | 0.324 Å |
| heavy atoms, **FPS Bondi radii** | 3 178 | 1.00 | 0.222 Å |
| **all atoms + Bondi** (what FPS reads) | 2 991 | **0.94** | **0.104 Å** |

And the volumes are not merely the same size, they are the same volume:
**100 %** of bff's voxels lie within one voxel (0.6 Å) of an FPS voxel, 99.8 %
within 0.52 Å — which is the largest offset two same-spacing lattices can have
— and 95.3 % within half a voxel. bff finds **no volume FPS does not**; it is
slightly *conservative*, by 6 %. The lattices never coincide exactly because
bff anchors on the **global absolute lattice** (PRD-105) and FPS on the source
atom, so an exact voxel-set comparison is the wrong metric and reports zero
overlap however well the two agree.

Both inputs matter and neither is free: FPS reads **all 17 733 atoms** where
`NonWaterNonHydrogenPDBSelector` gives 9 023, and FPS's radii are **Bondi**
(C 1.70, N 1.55, O 1.52, P 1.80) where IMP's `read_pdb` assigns united-atom
radii carrying implicit hydrogens (C 1.85–2.275).

**3. An `AV` whose clearance is too small returns an empty volume and says
nothing.** Unaffected by the above, and the one defect here that reaches users.
`get_is_valid()` answers `true`, no warning is logged, and
`get_mean_position()` returns **exactly half the source atom's coordinate**:

```
imp_bff av-export -p 3GUN.pdb -c A -r 132 -a CB --linker-width 4.5
  → A132 CB: mean position (0.68, -8.60, -2.73) A     # CB is (1.353, -17.196, -5.469)
  → .xyz first line: 0                                 # empty file, exit status 0
```

At the default width 1.5 the same command writes 2734 points. **4.5 Å is FPS's
standard linker width** — every position in both fixtures uses it — so this is
not an exotic input, and a silent empty volume feeds `InvalidR` (G3) a wrong
answer. With `linker_width = 4.5` and `dg = 0.6` the derived
`allowed_sphere_radius` is 1.5 and the volume is empty; 2.5 is still empty; 3.0
produces points. FPS's own `LinkerInitialSphere` is 0.5, so the two conventions
are not the same quantity — that mapping is the last piece of G8.

**A measurement trap, recorded so it is not repeated twice more:**
`AV::get_map().get_xyz_density()` returns **one entry per point**, not a flat
`x, y, z, w` array; dividing its length by four under-reports the volume by 4×.
`IMP.bff.write_av()` is the honest count.

## Non-goals

- **FPS's `SpringEngine` integrator.** D1.
- **The `.bin` project file.** Gzipped .NET `BinaryFormatter` of a
  `Dictionary<string, Dictionary<string, Option>>` (`OptionsManager.cs:287`).
  Reading it means implementing MS-NRBF in C++ for a format whose readable
  twin is written beside it on every save. Overturnable, but the cost is real.
- **Writing any legacy format.** Consistent with `FPSIO.h`: a decade of files
  must stay readable; nothing should produce another one.
- **`AVS` and `EDF` position types.** FPS parses them and computes neither.
- **The GUI.** The results grid, checkbox selection, clipboard copy and
  printing become files and flags. Stated plainly because "all functions of
  FPS" was the ask and these are the ones that will not feel identical.
