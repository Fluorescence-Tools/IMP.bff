# PRD-140: an abstract dataset — curves and 2-D/3-D/N-D data, with the noise on the data

**Status**: step 1 done 2026-09-08 -- `Dataset` exists (`include/Dataset.h`, 15 tests in `test/dataset/`): any rank, the noise *family* on the data, variance asked of the model, Pearson/deviance/Neyman residuals from one dataset, and a refusal where a stored family has nothing stored. **Step 2 done 2026-09-08**: a heterogeneous group composes *through the node graph* -- `test/dataset/test_joint_over_datasets.py`, four tests. **Not done**: the configured enum is still the default for `ChiSquared` and `JointChiSquared`, because chisurf sets it per fit (`core/fitting/minimizer.py`), so retiring it needs the sign decision below settled first. No N-D consumer yet either -- the rank-3 case is tested, not used. Owner's direction, in four
statements over one session: "isnt it better to have a more abstract curve
class"; "bff should be more abstract as it will also handle FCS curves, that
have different noise"; "so curves and 2d/3d/nd data must be abstract"; and,
on where the concrete models belong, "shouldnt tcspcdecay live in tttrlib".

**Read first**: [`okf/reference-cxx-nodes.md`](../reference-cxx-nodes.md) —
the eleven C++ node classes that exist and what they cover.

## Why

There are already two families of curve in this library and they do not
share an abstraction:

| | shape | noise |
|---|---|---|
| `TcspcDecay` | a decay over time channels | Poisson, or weighted least squares |
| `FcsMdfCurve`, `FcsSaturationCurve` | a correlation over lag times | **neither** — the variance of a correlation estimator, usually from splitting the measurement |

And a third family that is not a curve at all: `DensityGrid`,
`OccupancyGrid`, `PathMap`, `AVOccupancyMap`, and the `ng^3` fields the
diffusion solver propagates.

The noise model lives in the wrong place. `ChiSquared` carries a `NoiseModel`
enum and is *told* which to use — `"default"` or `"poisson"` — so the
objective knows something about the data that the data should have carried.
That is workable for one TCSPC curve and wrong the moment a joint objective
holds a decay and a correlation curve, because the right weights differ per
member and only the member knows them.

It is about to matter concretely. `../ucfret` fits eight to twelve histograms
of different lengths under a Poisson likelihood
(`okf/reference-bayesian-decay-model.md`), and the same stack fits FCS. A
`JointChiSquared` over both cannot be configured with one enum.

## What

1. **An abstract dataset**: values with a shape (`n`, `n×m`, `n×m×k`, …), an
   optional axis per dimension, and a **noise model that belongs to it**. A
   curve is the one-dimensional case and not a separate concept.

   **The dataset owns the noise *family*, not the per-point weights.** This
   distinction is the whole of the design and getting it wrong is quiet, so
   it has its own section below.
2. **An abstract model value** of the same shape, which is what a node
   produces. `TcspcDecay` and the FCS curves become producers of one.
3. **`ChiSquared` asks rather than is told.** Its residuals come from the
   dataset's noise model; the enum becomes a property of the data.
   `JointChiSquared` then holds members that disagree about noise, which it
   cannot today.
4. **The N-D case is not an afterthought.** An image, a correlation matrix and
   an `ng^3` density are the same abstraction at higher rank, and the grid
   classes above should be expressible as datasets rather than as five
   unrelated types.

## The trap: a weight is not a property of the data

Raised by the consumer (`../ucfret`, 2026-09-08) against the first draft of
this PRD, which said a dataset carries "Poisson, Gaussian with given weights,
correlation-estimator variance, or a caller-supplied weight array". That
sentence invites the bug.

For counting data the per-point weight is **not** a property of the data.
Weighting by the data, `1/y`, is Neyman chi-squared and is **biased**: it
pulls the fit toward the low bins, and the bias does not vanish as counts
grow. Weighting by the model, `1/λ`, is Pearson, and it is what the expected
Fisher information uses -- `Jᵀ diag(1/λ) J`, with `λ` from the model at the
current iterate. **So the weights change every iteration**, and a dataset that
owns per-point sigmas cannot express that.

The failure is silent, which is what makes it worth a section: the fit still
converges, to the wrong place, and a reduced chi-squared near one hides it.

So the interface must carry both shapes:

| | who knows the variance | example |
|---|---|---|
| stored | the dataset, once | Gaussian FCS with measured per-point sigmas |
| derived | the model, per evaluation | Poisson counts, `variance = λ` |

**Both are already present in this library**, which is the strongest argument
that the abstraction has to hold them. `weighted_residuals` in
`ChiSquared.cpp` has exactly two paths: `NOISE_NEYMAN` divides by a stored
error array supplied with the data, and `NOISE_POISSON` computes a signed
deviance residual from the data *and the model*. The second is already
"variance = f(model)"; the first is the stored-sigma case; and the enum's own
documentation says the default is "i.e. Neyman chi-square".

Two things to fix while passing:

- With no error array the stored path silently divides by 1.0 -- weighted
  least squares becomes unweighted least squares, with no complaint. Under
  the new abstraction a dataset with a stored noise model and no stored
  variance should refuse. **If the abstraction refuses in only one place,
  refuse here**, and the consumer's reason is better than mine: Neyman at
  least declares an intent, whereas unweighted least squares on counts
  spanning four decades -- which is every TCSPC histogram -- fits the peak and
  ignores the tail, and the tail is where the distance information lives.
- The consumer sums a Poisson log-likelihood, `Σ mask·(y log λ − λ)`, and uses
  Pearson residuals `(y−λ)/√λ` for its runs test rather than the signed
  deviance root. Deviance and log-likelihood agree as *objectives* -- the
  deviance is twice the difference from the saturated model, so minimising one
  maximises the other -- but they are different residuals, and a dataset that
  declares "Poisson" must let the caller ask for either. The dropped
  `−log(y!)` matters only for an absolute evidence, not for ratios.

## Found while building it: the two noise models disagree on a sign

`weighted_residuals` returns `(y − mu)/e` under `"default"` -- positive where
the data exceeds the model -- and the *opposite* sign under `"poisson"`, whose
`deviance_residual` sets `sign = (mu > y) ? +1 : −1`. Measured on
`y = [5, 10, 20, 3]`, `mu = [6, 9, 25, 3]`:

| | | | | |
|---|---|---|---|---|
| default | −0.4472 | +0.3162 | −1.1180 | 0 |
| poisson | +0.4205 | −0.3274 | +1.0365 | 0 |

**So switching noise model flips every residual**, and a residual plot or a
runs test flips with it. The magnitudes are right in both, so no objective and
no fit moves -- which is exactly why it has survived.

`Dataset` is internally consistent: Pearson, deviance and Neyman all read
positive where the data exceeds the model, and a test asserts that its
deviance magnitudes equal `ChiSquared`'s while the signs are opposed.
**Not fixed in `ChiSquared`**, deliberately: chisurf plots those signs today
(`chisurf/core/fitting/minimizer.py` sets the noise model per fit), so
flipping them is a visible change that wants its own decision. It is the first
thing to settle when the objective moves onto the dataset.

## Uncertainty propagation, because a constructed observable is not counts

Owner, 2026-09-08: chisurf builds a "fake" magic angle from a parallel and a
perpendicular channel and propagates the error for it, *"VV + 2*VH not poisson
anymore (because of the 2)"*, and then: *"need all type of operation"*.

Both are right and the second is what makes it a design rather than a special
case.

**The combination is not Poisson.** `VV + 2G VH` has variance
`VV + 4G^2 VH` -- the coefficient squares -- where a Poisson reading of the
result would say `VV + 2G VH`. The perpendicular channel is understated by a
factor of `2G`, and the misfit is pushed wherever the perpendicular counts are
largest.

**And propagating over the operands is not enough**, because the interesting
observables share their channels. Anisotropy is
`r = (VV - G VH)/(VV + 2G VH)`: the same two channels above and below the
line, so numerator and denominator are strongly correlated, and no amount of
care about each half fixes it.

So propagation is over the **independent sources**, with the derivatives
composed by the chain rule as the expression is built:

    Var(z) = sum_s (dz/ds)^2 Var(s)

`set_as_source` declares a measured channel; `add`, `subtract`, `multiply`,
`divide`, `affine` and `transform` compose. A source appearing on both sides
stays one source with its two derivatives summed, which is what makes the
correlation come out right without the caller thinking about it. The sharpest
check, and a test: `x - x` is exactly zero with exactly zero variance, where
independent propagation would give it `2 Var(x)`.

`transform` takes `f(a)` and `f'(a)` per point, so a transform this class does
not know -- a logarithm, a power, an instrument linearisation -- still carries
its uncertainty.

**One honesty about the Poisson case.** A Poisson source contributes its
*measured* values as its variance, because a combination cannot be decomposed
back into per-channel predictions: the model predicts `VV + 2G VH` and not the
two separately. That is data weighting, with the Neyman bias described above,
and it is the unavoidable price of constructing the observable. The unbiased
alternative is not to construct it -- keep the channels as two datasets, each
Poisson, and let one objective hold both. That the abstraction supports the
honest route is the argument for preferring it, and it should be said wherever
this is documented for users.

## Producers, and what sits after them

Also from the consumer, and it generalises better than the special case that
prompted it. A dataset has **one noise model and several model producers,
summed**. What decides how many producers:

> Contributions that pass through **different instrument responses must be
> separate producers**; contributions that share a response are **one**
> producer, because the model is linear in the amplitudes and they can be
> summed before the convolution.

So a quenched donor and a donor-only fraction are one producer; a sensitised
acceptor and a directly excited one are one; scatter and a flat background are
one. An interleaved histogram whose two pulses have different offsets is two
producers and a sum -- not because it is a special case, but because the rule
says so.

And a third category that is neither producer nor noise: **transforms applied
after the sum**, multiplying the finished curve. A DNL linearisation table is
one; a per-channel discrepancy term is another. The abstraction should have a
place for them or say that it does not.

## Where `TcspcDecay` belongs, since it was asked

**The kernel is already tttrlib's.** The periodic reconvolution is
`fconv_per_cs_ad<double>` from tttrlib's spectroscopy module, vendored at
`include/internal/DecayConvolution.h`. It was said to be "kept in step" and
nothing checked it; `test_vendored_headers.py` now does, and the three copies
(MlpCore, LatticeDiffusion, DecayConvolution) are identical to tttrlib's as
of today.

**The node cannot follow it down as things stand**, and the reason is the
layering rather than the subject matter. `Node` and `Port` live in bff;
tttrlib is *below* bff and has no equivalent — and bff does not even link
tttrlib, it vendors headers from it. Moving `TcspcDecay` to tttrlib means
moving the dataflow framework there too, which makes the photon library the
home of a graph engine.

**Settled by the owner, 2026-09-08**: *"no dataflow stays bff, tttrlib is
photon processing (data reduction, io, etc) bff is dataprocessing."* So the
line is drawn by what a library is for rather than by where a class currently
sits: **tttrlib reduces photons to data; bff processes data.** `Node`, `Port`
and `EvaluationGraph` stay here, `TcspcDecay` stays here, and the
reconvolution kernel stays tttrlib's and stays vendored. The rest of this
section records the two answers that were considered, because the reasoning
outlives the decision.

The two candidates were:

- **Move `Node`/`Port` down to tttrlib.** Then every curve-level node lives
  with its mathematics, and bff keeps the coordinate-level ones. Legal —
  bff is above tttrlib — but it makes tttrlib own a general dataflow
  mechanism that has nothing photon-specific in it.
- **Keep the nodes in bff and make them thin.** The mathematics stays
  vendored or linked from tttrlib, the node is a shell over it, and what bff
  contributes is exactly the abstraction this PRD is about. `TcspcDecay`'s
  own header already argues this shape: "what this class contributes is the
  graph — ports, ordering".

The second is the ruling, and it is what `TcspcDecay`'s own header already
argues: "what this class contributes is the graph -- ports, ordering".

**What that makes bff responsible for**, and it is the whole of this PRD: the
abstraction over what is processed. A dataset with a shape and a noise family;
model producers; the graph that evaluates them. tttrlib owns getting from
photons to a histogram or a correlation curve, and the mathematics that
operates on one; bff owns everything that treats that result as data to be
modelled, fitted and reported.

## Done when

- A dataset with a shape and a noise model exists, and a curve is the rank-1
  case rather than its own class.
- `ChiSquared` derives its residuals from the dataset rather than from a
  configured enum, and the existing TCSPC results are unchanged — the same
  numbers, from the data's own declaration.
- **Done 2026-09-08.** `JointChiSquared` holds a Poisson decay and an FCS
  curve at once and weights each correctly, which is the check that could not
  pass before -- `test/dataset/test_joint_over_datasets.py`. It needed no
  change to `JointChiSquared` itself: a member's dataset reaches the group
  through `ChiSquared::evaluate`, so the node was already composing whatever
  weighting its members carried. Proven through the graph rather than through
  `compute_chi2`, because that is the path `Minimizer` takes: `update()`, the
  ports read, and one Levenberg-Marquardt run recovering a lifetime shared
  between a Poisson dataset and a Gaussian one (chi2 2081 -> 0.094 over 48
  residuals). The blocks stay separable and carry *different* residual
  definitions in one vector -- deviance for the counts, Pearson for the
  correlation curve.
- At least one N-D case — a `DensityGrid` or an `ng^3` field — is expressed
  as the same dataset, so that "curves and N-D data are abstract" is a fact
  about the code rather than an intention.
- The eleven existing node classes still pass their tests.

## The same pattern on the other side of the boundary

Recorded because it says how easily this happens, not to assign anything.
Having been warned, the consumer audited its own repository and found the
shape twice: a selectable Gaussian score whose variance comes from the data,
`(y − mu)/√max(y,1)` -- Neyman as an objective, explicitly chosen but not
named as such -- and a *reported* reduced chi-squared weighted the same way,
which is Neyman in a diagnostic. Their own rule-zero residual is Pearson. So
one repository computes "weighted residuals" two different ways and only one
of them is what its own rule means. Their default path is the plain Poisson
log-likelihood and is correct, and their measured results do not touch the
others.

The lesson for this PRD is that "weighted residuals" is not one thing, and
that a library which offers the phrase without naming the weighting invites
exactly this. Whatever the abstraction exposes should be named for its
weighting -- Neyman, Pearson, deviance -- and not for being weighted.
