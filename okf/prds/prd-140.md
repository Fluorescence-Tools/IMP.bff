# PRD-140: an abstract dataset — curves and 2-D/3-D/N-D data, with the noise on the data

**Status**: written 2026-09-08, not started. Owner's direction, in four
statements over one session: "isnt it better to have a more abstract curve
class"; "bff should be more abstract as it will also handle FCS curves, that
have different noise"; "so curves and 2d/3d/nd data must be abstract"; and,
on where the concrete models belong, "shouldnt tcspcdecay live in tttrlib".

**Read first**: [`okf/reference-cxx-nodes.md`](../reference-cxx-nodes.md) —
the eleven C++ node classes that exist and what they cover.

## Why

There are already two families of curve in this library and they do not
share an abstraction:

| | shape | noise |
|---|---|---|
| `TcspcDecay` | a decay over time channels | Poisson, or weighted least squares |
| `FcsMdfCurve`, `FcsSaturationCurve` | a correlation over lag times | **neither** — the variance of a correlation estimator, usually from splitting the measurement |

And a third family that is not a curve at all: `DensityGrid`,
`OccupancyGrid`, `PathMap`, `AVOccupancyMap`, and the `ng^3` fields the
diffusion solver propagates.

The noise model lives in the wrong place. `ChiSquared` carries a `NoiseModel`
enum and is *told* which to use — `"default"` or `"poisson"` — so the
objective knows something about the data that the data should have carried.
That is workable for one TCSPC curve and wrong the moment a joint objective
holds a decay and a correlation curve, because the right weights differ per
member and only the member knows them.

It is about to matter concretely. `../ucfret` fits eight to twelve histograms
of different lengths under a Poisson likelihood
(`okf/reference-bayesian-decay-model.md`), and the same stack fits FCS. A
`JointChiSquared` over both cannot be configured with one enum.

## What

1. **An abstract dataset**: values with a shape (`n`, `n×m`, `n×m×k`, …), an
   optional axis per dimension, and a **noise model that belongs to it** —
   Poisson, Gaussian with given weights, correlation-estimator variance, or a
   caller-supplied weight array. A curve is the one-dimensional case and not
   a separate concept.
2. **An abstract model value** of the same shape, which is what a node
   produces. `TcspcDecay` and the FCS curves become producers of one.
3. **`ChiSquared` asks rather than is told.** Its residuals come from the
   dataset's noise model; the enum becomes a property of the data.
   `JointChiSquared` then holds members that disagree about noise, which it
   cannot today.
4. **The N-D case is not an afterthought.** An image, a correlation matrix and
   an `ng^3` density are the same abstraction at higher rank, and the grid
   classes above should be expressible as datasets rather than as five
   unrelated types.

## Where `TcspcDecay` belongs, since it was asked

**The kernel is already tttrlib's.** The periodic reconvolution is
`fconv_per_cs_ad<double>` from tttrlib's spectroscopy module, vendored at
`include/internal/DecayConvolution.h`. It was said to be "kept in step" and
nothing checked it; `test_vendored_headers.py` now does, and the three copies
(MlpCore, LatticeDiffusion, DecayConvolution) are identical to tttrlib's as
of today.

**The node cannot follow it down as things stand**, and the reason is the
layering rather than the subject matter. `Node` and `Port` live in bff;
tttrlib is *below* bff and has no equivalent — and bff does not even link
tttrlib, it vendors headers from it. Moving `TcspcDecay` to tttrlib means
moving the dataflow framework there too, which makes the photon library the
home of a graph engine.

So there are two coherent answers and the abstraction chooses between them:

- **Move `Node`/`Port` down to tttrlib.** Then every curve-level node lives
  with its mathematics, and bff keeps the coordinate-level ones. Legal —
  bff is above tttrlib — but it makes tttrlib own a general dataflow
  mechanism that has nothing photon-specific in it.
- **Keep the nodes in bff and make them thin.** The mathematics stays
  vendored or linked from tttrlib, the node is a shell over it, and what bff
  contributes is exactly the abstraction this PRD is about. `TcspcDecay`'s
  own header already argues this shape: "what this class contributes is the
  graph — ports, ordering".

This PRD assumes the second and should say so if that is wrong, because
everything below depends on it.

## Done when

- A dataset with a shape and a noise model exists, and a curve is the rank-1
  case rather than its own class.
- `ChiSquared` derives its residuals from the dataset rather than from a
  configured enum, and the existing TCSPC results are unchanged — the same
  numbers, from the data's own declaration.
- `JointChiSquared` holds a Poisson decay and an FCS curve at once and
  weights each correctly, which is the check that could not pass before.
- At least one N-D case — a `DensityGrid` or an `ng^3` field — is expressed
  as the same dataset, so that "curves and N-D data are abstract" is a fact
  about the code rather than an intention.
- The eleven existing node classes still pass their tests.

## What to establish before starting

- How many callers configure `ChiSquared`'s noise model today, and whether
  any rely on overriding what the data would say.
- Whether the FCS curves' noise is currently modelled anywhere at all, or
  whether joint FCS fitting has simply never weighted correctly.
- Whether `Node`/`Port` moving to tttrlib is on the table, since it decides
  where the concrete models live and this PRD assumes it is not.
