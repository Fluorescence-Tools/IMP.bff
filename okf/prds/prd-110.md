## The problem is the inverse problem

The forward solve is not slow enough to be worth replacing on its own.
Measured 2026-08-17 on the shared box, `GridDiffusionSolver`, `ng = 41`,
`dg = 1 Å`, `D = 8 Å²/ns`:

| | |
|---|---|
| 50 ns of donor decay | 4 800 steps, **2.26 s** |
| stability limit | `dt ≤ dg²/(6D)` = 0.0104 ns |
| scaling in resolution | steps ∝ `dg⁻²`, voxels ∝ `dg⁻³` → **`dg⁻⁵`** |

So halving the voxel edge is ~32× the work, and a 2 Å → 1 Å refinement takes a
2 s solve to about a minute. Still tolerable **once**. The trouble is that it is
never once:

* **Calibration.** `PET_QUENCHING_REFERENCE` ships with the sentence *"starting
  values meant to be calibrated against measured lifetimes, not fixed
  constants"* (Peulen 2017). Calibrating six `kQ` values plus `D`, the
  stickiness factor and a contact distance against a measured decay is a
  9-parameter fit. A derivative-free local optimiser wants O(10²–10³)
  evaluations; each is a full solve. **One site becomes an hour, and the point
  of calibration is that it is done per dye and per construct.**
* **Scanning.** QuEst scans every labelling position — 151 on 148l chain E.
  Calibration × scan is the product, not the sum.
* **Uncertainty.** Nobody currently quotes an error bar on a predicted
  lifetime, because propagating parameter uncertainty means sampling the
  parameter space, which means re-solving.

A surrogate that is **differentiable in the parameters** turns all three from a
search into a gradient step. That, not raw forward speed, is the case for this
work — and it is the case that has to be tested first (stage 0).

## What is actually being learned

The field model, exactly as PRD-109 implements it:

    ∂p/∂t = ∇·(D(r; θ) ∇p) − k(r; θ) p        on Ω
    n̂ · (D ∇p) = 0                            on ∂Ω        (no flux: the dye
                                                            cannot enter protein)
    p(r, 0) = p_eq(r; θ)                       (the equilibrium occupancy)
    F(t) = ∫_Ω p(r, t) dr                      (the observable — the decay)

with parameters

    θ = ( D_free, slow_factor, contact_distance,
          kQ[TRP, TYR, MET, HIS, CYS, PRO], rC, τ₀ )

The network is `N(r, t, θ) → p`, trained on the PDE residual rather than on
solver output alone. Two constraints are imposed **structurally**, not through
loss terms, because a soft constraint on an initial condition is the classic way
a PINN learns a plausible field that is not the solution:

* **Initial condition, exactly**: `p = p_eq(r; θ) + t · Ñ(r, t, θ)`, so
  `p(r, 0) = p_eq` identically.
* **Domain, exactly**: multiply by the occupancy mask (or a smoothed level set
  of it), so `p ≡ 0` outside Ω whatever the network does.

Left in the loss: the PDE residual, the no-flux condition on ∂Ω, and a
supervised term on `F(t)` against the solver.

## The crux: geometry is not a parameter

**A PINN is the right tool for a fixed domain and varying parameters. It is the
wrong tool for varying geometry**, and every labelling site is a different
geometry. This is the decision that shapes the whole PRD, and it should be
faced rather than discovered in stage 2:

| | Fixed Ω, varying θ | Varying Ω |
|---|---|---|
| Right tool | **parametric PINN** — this PRD | a **neural operator** (DeepONet / FNO) trained on solver output |
| Training data | none needed (residual only) | thousands of solves |
| What it buys | per-site calibration in seconds | per-site prediction with no solve |
| Risk | moderate | high — needs the dataset first |

The honest scope is therefore **per-site**: train a surrogate for *one* site's
geometry, parametric in θ. That already delivers the calibration case, which is
where the cost is. Conditioning on geometry is a separate, larger PRD and
should not be smuggled into this one.

## Where it lives — the open question

`IMP.bff` ships through conda-forge **as part of IMP**, where the runtime
dependency list is a public contract. That is why numba is optional (`_jit.py`)
and why PRD-109 declined to bring ChiSurf's OpenCL backend across. **A deep
learning framework is a much larger ask than numba**, and unlike numba it
cannot degrade: a PINN without an autodiff engine is not a slow PINN, it is
nothing.

Three options, none free:

1. **`IMP.bff.quenching.surrogate`, torch as an optional extra.** Consistent
   with where the physics lives, and the ground truth (`GridDiffusionSolver`)
   is right there. Cost: a subpackage that hard-errors without torch, which no
   other part of `IMP.bff` does.
2. **ChiSurf.** Top of the stack, already heavy, already the fitting layer —
   and calibration *is* fitting. Cost: the model's input is coordinates, which
   the placement rule sends to `imp.bff`; and ChiSurf would then own physics
   that PRD-109 just finished moving out of it.
3. **A sibling repo.** Clean dependency story, one more checkout, and the
   ground truth is then across a repo boundary.

**Recommendation: (1), with the extra named and the import hard-failing with a
message that says what to install.** The placement rule is about *input*, the
input is coordinates and parameters, and splitting a surrogate from the solver
it approximates is how the two drift. But this is the owner's call, and it is
the one that most affects everything downstream.

## Decisions needed before stage 0

1. **Where it lives** (above). Blocking.
2. **Framework.** torch vs jax. jax's `grad`/`vmap` fit residual-based training
   and parameter sweeps more naturally; torch is far more likely to already be
   installed. No strong recommendation — the code should be small enough that
   this is not irreversible, and stage 0 should be written to find out.
3. **Is the surrogate a *product* or a *tool*?** If a calibrated `kQ` set is
   the deliverable, the surrogate can stay a development instrument and never
   ship — which removes the dependency problem entirely and is worth
   considering seriously.
4. **Accuracy target.** Proposed below; it needs a number the owner will
   actually accept, because "close to the solver" is not a specification.

## Stages

### Stage 0 — establish that the premise is true (no network)
**Before writing a single layer.** Measure the thing this PRD claims:

* Build the calibration loop as it exists today — fit `kQ` and `D` to a
  synthetic decay generated by the solver at known parameters, using the solver
  itself. Record: number of evaluations, wall-clock, and whether it recovers
  the known parameters at all.
* Establish the **identifiability** of θ from a single decay curve. This is the
  result that decides the PRD's fate and it needs no machine learning: if `kQ`
  and `slow_factor` are degenerate against one decay — and they plausibly are,
  since both act by keeping the dye near quenchers — then a faster surrogate
  fits a degenerate problem faster and nothing improves. Sensitivity via the
  Fisher information of `F(t)` with respect to θ, and the condition number of
  its covariance.

**Gate: if θ is not identifiable from the available observables, this PRD stops
here** and is replaced by one about what to measure instead (e.g. anisotropy,
or decays at several sites jointly).

### Stage 1 — a fixed-θ PINN on one site, against a validated solver
The smallest thing that can be wrong in an informative way. One site, one θ,
hard-constrained IC and domain, residual + observable loss.

Acceptance, against `GridDiffusionSolver` — which PRD-109 pinned to *analytic*
results (⟨x²⟩ = 2Dt to 0.1 %, mass conserved to 1e-9, a uniform rate recovered
to 1 %), so it is a trustworthy reference:

* `F(t)`: **≤ 1 % relative error** over the first three lifetimes.
* the recovered mean lifetime: within **0.02 ns**.
* mass conservation with `k ≡ 0`: within **1 %** over 50 ns.
* the field itself, not just the observable: relative L² error ≤ 5 % on Ω.

The last one matters. A network can fit `F(t)` — a scalar per time point — with
a field that is wrong everywhere, and reporting only the observable would hide
it.

### Stage 2 — parametric in θ, one site
`N(r, t, θ)`, θ sampled over the calibration ranges. Acceptance: stage 1's
bounds held at **held-out θ**, plus the gradient `∂F/∂θ` checked against finite
differences of the solver to **≤ 5 %** — because the gradient, not the value,
is what the calibration actually consumes.

### Stage 3 — calibration, end to end
Fit θ to a measured decay through the surrogate, then **verify the answer with
the solver**. The surrogate is a search accelerator, never the last word: the
reported parameters must be the ones the true forward model reproduces.
Acceptance: recovers known θ from synthetic data within stage 2's tolerance,
and the wall-clock beats stage 0's baseline by ≥ 10× including training.

### Stage 4 — uncertainty (only if 0–3 land)
Parameter covariance from the surrogate's Hessian, propagated to a predicted
lifetime, validated against solver-based sampling on a few points.

## Non-goals

* **Replacing the solver.** It stays the ground truth and the reporting path.
* **Geometry conditioning / neural operators.** Named above; separate PRD.
* **Replacing the particle model.** The Brownian walk resolves the dye's
  history and can produce a correlation function; a field surrogate cannot.
* **Shipping a trained model as data.** Weights fitted to one geometry are not
  a library asset.

## How this fails

Stated in advance so the stages can be read against it:

* **θ is not identifiable** — the most likely failure, and stage 0 is designed
  to find it before any modelling. A faster fit to an under-determined problem
  is not progress.
* **The PINN is slower than the solver, all in.** Training cost has to be
  amortised over the calibration; if training takes longer than the ~10³ solves
  it replaces, there is nothing here. Stage 3's acceptance is exactly this.
* **It fits `F(t)` with the wrong field.** Guarded by the stage 1 L² criterion.
* **The dependency is refused** — a legitimate outcome, and decision 3 (a
  development tool rather than a shipped feature) is the graceful version of it.
