# Dihedral rotamer libraries (`.drot`)

**Status:** active (2026-08-24)
**Done:** The `.drot` store: the format, the reader and writer, the shipped containers, and the Dunbrack-style dihedral encoding.
**Missing:** The continuous side-chain generator (driver b).
**Next:** Driver b.


## Why

The shipped rotamer libraries store every rotamer as a full-coordinate frame
(`<stem>_cutoff<N>.bcif`, ~4 bytes/coordinate). For `A48_C1R_cutoff10` that is
711 rotamers × 83 atoms × 3 coords ≈ 708 KB. But a dye+linker is mostly rigid:
the rings do not move and only a few linker-chain single bonds rotate between
frames. FASPR (cloned at `junk/FASPR/`) exploits exactly this — one template +
a handful of χ dihedrals + a weight per rotamer (≈ 20 B/rotamer), rebuilding
coordinates on demand through `Internal2Cartesian` (`junk/FASPR/src/Utility.cpp`).

Re-encoding the rotamer libraries the same way buys two things:

- **(a) small, fast-load libraries** — the `.drot` (v2) of `A48_C1R_cutoff10`
  is 253 KB against 765 KB of `.dcd` (0.33x), lossless to the int grid: the
  frame's base + θ + φ reproduce the source to ~0.01 A and keep transition
  dipoles to ~0.1 deg.
- **(b) a continuous side-chain generator.** Expose the per-rotamer dihedrals
  so *arbitrary* dihedral combinations build into full coordinates. That is
  what more accurate dye–quencher sampling needs (FASPR's `SideChain(site,
  rot, rxyz)` builds any rotamer, not just stored bins).

## What the `.drot` format is

One rigid template (`<stem>.pdb`, already shipped, shared across cutoffs) plus
a binary dihedral store `<stem>_cutoff<N>.drot`:

- **header** — magic, version, `n_atoms`, `n_rotamers`, `n_rotors`,
  cluster_threshold;
- **rotor definitions** — each rotor = its 4 dihedral-defining atoms + the
  rotating subtree index set. The rotor set **rides in the file**, not
  hardcoded, so any of the 34 dye×linker combos (`C1R…C3R`) encodes without
  code changes;
- **dihedral table** — `n_rotamers × n_rotors` dihedrals, `int16` at 0.1°
  (FASPR-style);
- **weights** — one `float` per rotamer.

## Provenance

Every shipped entry is FRETpredict's (author Montepietra et al., GPLv3,
`data/rotamer_library/libraries.json`). The FRETpredict parity pins
(`test/references/cgdye_fretpredict_pins.json`) are pinned *to them*. Re-encoding
must therefore reproduce the shipped frame within a stated tolerance — **not**
change them — and the parity pins must **still pass** after the format change.
The `.drot` is the same ensemble in a different store; it is not a different
object until stage 3's generated side-chains land.

## Already exists (close nothing)

| piece | where | what it does |
|---|---|---|
| `cluster_frames_operator` | `IMP.bff` (C++, exposed) | greedy leader clustering by unaligned RMSD — **the exact algorithm FRETpredict's libraries are built with** (`include/Clustering.h:29`). No port needed |
| `rms_no_align` | same | the metric the clustering runs under |
| `load_retamer_library_dcd` | `pyext/IMP_bff.dyesampling.i` | reads a PDB + DCD/BCIF trajectory + weights into (n_rot, n_atom, 3) coords; DCD is IMP-native |
| `bin/imp_bff_traj2bcif` | `bin/` | the trajectory→BCIF writer (the today's store) |
| `MolecularGraph::get_dihedrals` | C++ (`src/MolecularGraph.cpp`) | bond-connectivity-derived dihedrals |

The rotor-graph derivation exists; what is **missing** is the inverse —
internal-coordinate → cartesian reconstruction (FASPR's `Internal2Cartesian`).
That is the genuinely new primitive, and it is deferred to the C++ stage.

## Input contract

*(The verified conversion commands — DCD recovery, encode, validate, batch,
raw-MD route and its caveats — are in
[`prototypes/drot_rotlib/CONVERTING.md`](../prototypes/drot_rotlib/CONVERTING.md).)*

- **One trajectory input: `.dcd`** (IMP-native). The encoder reads `.dcd` only;
  any non-DCD format is a caller's `mdtraj` conversion, out of scope.
- The `.dcd` **may be raw (un-clustered) or already clustered**, decided by the
  frame count vs the weights file:
  - `n_frames == len(weights)` → already clustered, encode directly;
  - otherwise → cluster with `cluster_frames_leader`, **leaders are the
    rotamers and weights = cluster populations** (`rotamer_cluster_weights`).
  This links counting and clustering in the encoder.
- Optional explicit weights file is still honoured when provided.
- **Keep-all rotamers**: no FASPR-style <1% prior floor — the weights are
  Boltzmann from screening, and the AV use needs real weights.

The 95 shipped `.dcd` are recoverable from git commit `8fac573` (the
four-repository split); the one raw MD, `A48_C1R/traj.xtc`, exercises the
clustering path.

## Stages

### Stage 0 — prototype: rotor kernels (`rotlib.py`)
Pure-python/numba kernels in `prototypes/drot_rotamer/`:
- rotor discovery from the template bond graph (acyclic single bonds holding a subtree),
- `coords_from_dihedral(template, rotors, chi)` — reconstruction (FASPR `Internal2Cartesian` analog),
- `frame_to_dihedral(template, rotors, frame)` — fit a frame's dihedrals.

### Stage 1 — prototype: encoder (`encode_droft.py`)
`.pdb` + `.dcd` (+ optional weights) → `.drot`, via AUTO-detecting raw vs
clustered and clustering when raw. Header + rotor defs + dihedral table + weights.

### Stage 2 — prototype: validation (`validate_drot.py`)
Reconstruct from `.drot` and compare vs the source `.dcd` frames RMN
(a part outside the fitted rotors). Produces a tolerance table across all 34
libraries. **This table is the go/no-go gate** for "rigid template +
dihedral" holds.

### Stage 3 — the `.drot` loader lands in IMP.bff (the C++ port, later)
Deferred because `src/` is in flux (PRD-117). When it moves:
- `coords_from_dihedral` C++ kernel + `%apply` numpy wrap,
- `rotamer.i` loader hook so `load_rotamer_library` reads `.drot` and returns
  the existing dict shape (`coords, weights, atom_names, resnames, metadata`),
- regenerate all 34 libs as `.drot`, keep `.bcif` a read path for user libs.

- [x] **The container is the stack's container** (2026-08-24, v10). The
  members no longer ride a private tar: they are the attached objects of a
  **PTO** document — EBML, `DocType "pto"` — so a rotamer library is framed by
  the same grammar as tttrlib's photon streams (`.mmfbd.pto`) and chimol's
  structures (`.chm.pto`), and the file is named `<stem>.drot.pto` after the
  profile-suffix convention PRD-040 settles. `include/Pto.h` + `src/Pto.cpp`
  are a **vendored** core written from
  `../tttrlib/okf/specs/pto-binary-decoding.md`, not a dependency on tttrlib —
  the rule the convergence record sets; ~570 lines, the size chimol's Python
  walker is. No element ID was invented: the eight members are `PtoKind`
  strings (`drot.header`, `drot.template`, `drot.rows`, `drot.grid` x4,
  `drot.weights`), which is the extension point the grammar already has.

  **The envelope is free.** Compressing each member on its own instead of one
  brotli stream over the tar costs *nothing* over the 95 shipped libraries —
  **19.60 MB against 19.64 MB** — because tar's 512-byte headers go away and
  pay for the joint context; per file it is +0.5 % (a one-rotamer library pays
  35 % of its 2 KB for the envelope, which is the whole cost). What it buys:
  one grammar to maintain, payloads on 8-byte boundaries for a mapping reader,
  a header a reader can inflate without the grids, and objects addressable by
  name and kind.

  **Proved against implementations that are not ours**, which is the point of
  a shared format: `pto_ebml_check` walks all 95 with **libebml** (the
  reference implementation, `--aligned` enforced) and chimol's independent
  Python `PtoReader` walks all 95 and agrees on every object's kind, offset
  and payload. Round-trip is bit-exact against the v9 files (0.0 A), re-writes
  are byte-identical, and the FRETpredict pins and the 797-test suite are
  unmoved. v5-v9 still read; only v10 is written.
- [x] **All three rotamer families, one container each** (2026-08-24). The
  question the store had never answered: dyes were shipped, spin labels were
  convertible, side chains were not in the format at all. Now
  `data/rotamer_library/` holds **`dyes.drot.pto`** (95 libraries, 19.7 MB),
  **`spinlabels.drot.pto`** (10 DEER-PREdict spin labels, 0.24 MB) and
  **`sidechains.drot.pto`** (the Dunbrack-2010 backbone-dependent table, 18
  residues, 3.3 MB) -- one file per family, which is what changes together.

  **Bundling is a copy.** `write_drot_bundle` moves payload bytes across
  unread under names prefixed `<library>/` and writes a `drot.catalog`; the
  family container is 19,675,419 bytes against the 19,683,305 of the 95
  separate files, the difference being the EBML headers it no longer repeats.
  A library is addressed by a **locator**, `dyes.drot.pto::A48_C1R_cutoff10`,
  which the resolver answers with and every loader takes. Reading one library
  out of ninety-five costs that library: `PtoReader` was changed to walk the
  framing by seeking (element headers only, ~12 octets each) and to read a
  payload only when asked. The 2026-08-23 rejection of "one corpus archive"
  was a property of the tar, and it does not survive the envelope.

  **Side chains are a different payload in the same grammar**, which is the
  claim the shared container makes and this is the case that tests it. A dye
  library is an ensemble; a side-chain library is a distribution over (phi,
  psi) -- so `rot.bbdep.header` and `rot.bbdep.records` join `drot.grid`, and
  again no element ID was invented. The records are FASPR's own 20-byte
  layout kept byte for byte: `write_dunbrack_bin` reproduces
  `dun2010bbdep.bin` with an identical SHA-256, which is why `faspr_pack` can
  take the shipped container (it unpacks a scratch copy for the vendored
  engine, which seeks by byte offset) and pack **byte-identically** to
  packing from the binary -- the parity pin is untouched. 13.76 MB becomes
  3.31 MB (0.241x). The decode was checked against the prototype's
  independent reader over 720 (residue, phi, psi) cases: exact, 0.0 deg.

  Licence, recorded rather than assumed: the Dunbrack library is
  academic-use, redistributed here on the owner's explicit instruction after
  the terms were flagged; the attribution, citation and terms travel *inside*
  the container in `bbdep.json`, so the notice cannot be separated from the
  data. Tests: `test/io/test_dunbrack.py` (9), plus the family round-trip in
  `test/io/test_drot.py`.

  **The pins did not have to be re-derived — the format had to stop losing.**
  The v8 rung rebuilt on *template* bond lengths, and real MD flexes bonds by
  ~0.004 A RMS: measured over the corpus that is 0.016 A of the 0.020 A total
  reconstruction error, which moved the FRETpredict pins by 1.3e-3 in E
  against their 2e-5 tolerance (10 cgdye failures). Storing the conformer's
  own bond length per row makes the representation complete (decode is exact
  to ~1e-13), so the only remaining error is the grid: **v9 = float32
  internals, column-major, byte-plane shuffled**, 1.2e-6 A mean / 9.3e-6 A
  max, 0.66x the `.bcif`, **and the pins pass unchanged**. Measured
  alternatives, all rejected: int16 delta grids for r/theta with int32 phi
  (0.46x, 1.8e-4 A — still inside the range that moved `traj2bcif`'s pins),
  float32 without the byte shuffle (0.72x), delta-from-template floats
  (0.87x, worse — small values are not smaller floats). The compact int16
  rung survives as an option (`--grid`, 0.30x, ~3e-3 A) with the same
  warning `imp_bff_traj2bcif` carries: dipole directions do not average
  their errors away.

  The shared kernel grew with it: `ZMatrix::frame_internals` /
  `decode_internals` (`include/ZMatrix.h`) measure and rebuild all three
  degrees of freedom per row, so `.drot` and a FASPR side chain still place
  atoms with the same primitive.

### Revision note (same day)
v1 stored only the *moving* dihedrals and dropped the base atoms; a
dihedral-only store reproduced the shipped MD at 2-5 A RMSD and ~22 deg dipole
error, which looked like a hard floor. It was a format gap: this MD also flexes
bond angles (~3 deg/row), so v2 stores the frame's own base coordinates + θ +
φ per row and is **lossless to the int grid**. The conclusion flipped: `.drot`
is a candidate drop-in for `.bcif`; the remaining work is the C++ port + pin
re-derivation.
