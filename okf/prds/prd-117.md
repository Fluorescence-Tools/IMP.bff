# PRD-117: `%pythoncode` to C++ — the JS/SWIG port

**status: in progress (started 2026-08-21).** `pyext/src/` went from 9,327 lines (30
`.py` files) to 353 lines (3 thin re-exports + `api.py`). The real code now lives
in C++ headers or in `.i` file `%pythoncode` blocks. This PRD eliminates the
`%pythoncode` blocks — all 11,607 lines across 29 files — by porting every one
to pure C++.

## Why

`%pythoncode` blocks are Python-only. The code must run via SWIG for JavaScript,
not just Python. SWIG wraps C++ for any target language; `%pythoncode` does not.
Every `%pythoncode` block must become C++ that SWIG can generate bindings for.

## Current state

`pyext/src/` is effectively done (353 lines of thin re-exports + lazy-import
infrastructure). The remaining work is entirely in `.i` files.

### Categories of `%pythoncode` content

1. **IMP API glue** (~4,200 lines): calls IMP C++ API objects through SWIG
   (`IMP::core::DistanceRestraint`, `IMP::atom::MolecularDynamics`,
   `IMP::rmf::load_frame`, etc.). C++ can call them directly.
2. **numpy shims** (~2,000 lines): reshape flat `std::vector<double>` to expected
   shape. C++ returns the right shape natively.
3. **dict/JSON bridges** (~1,500 lines): Python dicts to C++ typed objects. C++
   takes JSON or typed structs.
4. **File I/O** (~1,000 lines): Python file operations. C++ file I/O.
5. **Pure math** (~800 lines): C++ math.
6. **String parsing** (~600 lines): C++ string parsing.
7. **Data containers** (~500 lines): C++ structs.
8. **Lazy class defs** (~200 lines): C++ classes (no lazy needed without Python
   import order).

**None of these categories genuinely requires Python.**

## Porting strategy

### Approach: one C++ source file per `.i` file

Each `.i` file currently has `%pythoncode` blocks. The port creates a
corresponding C++ source file (e.g., `src/Sim.cpp`, `src/Docking.cpp`) that
replaces the Python with equivalent C++. The `.i` file keeps its SWIG typemaps
and `%include` directives but drops all `%pythoncode` blocks.

The `.i` file becomes a thin SWIG wrapper: typemaps, `%include` of the new C++
header, and nothing else.

### Dependency order

The `.i` files are included in `swig.i-in` in a specific order. C++ headers
defined earlier are available to headers defined later. The port should respect
this, but since C++ has proper `#include`, the ordering constraint is weaker
than in Python.

### File structure per ported module

For each ported module:

1. **Header** (`include/ModuleName.h`): C++ class or free functions that replace
   the `%pythoncode` logic. Uses existing C++ types from `include/` as building
   blocks.
2. **Implementation** (`src/ModuleName.cpp`): the implementation.
3. **SWIG wrapper** (`pyext/IMP_bff.module.i`): strips `%pythoncode`, keeps
   `%include "include/ModuleName.h"` and any needed typemaps.
4. **Registration** (`src/Files.cmake`): add `src/ModuleName.cpp`.

### Patterns for common categories

**numpy shims → native C++ return:**
```cpp
// Before (%pythoncode): reshapes flat vector to (N, 3)
// After (C++): returns std::vector<std::array<double, 3>> directly
std::vector<std::array<double, 3>> get_rotamer_centers(int site_index);
```

**IMP API glue → direct C++ API calls:**
```cpp
// Before (%pythoncode): IMP.atom.Molecule(m).get_particle()
// After (C++): directly holds IMP::atom::Molecule, calls .get_particle()
```

**dict/JSON bridge → typed structs:**
```cpp
// Before (%pythoncode): Python dict → DyeForceFieldSystem
// After (C++): DyeForceFieldSystem already exists, parse JSON directly
DyeForceFieldSystem forcefield_from_cif(const std::string& cif_path);
```

**Lazy class → C++ class:**
```cpp
// Before (%pythoncode): lazy-loaded class definition
// After (C++): regular C++ class, SWIG wraps it
class RotamerEnsemble : public States { ... };
```

### Callable API change

Two functions take Python callables:
- `radial_diffusion_map` (in `quenching.i`)
- `read_evaluators_json` (in `fps.i`)

These need an API redesign: instead of `Callable[[float], float]`, take a
pre-evaluated array of values, or a C++ `std::function<double(double)>`. For
SWIG/JS, the array-of-values approach is simpler.

## Build

- Source files listed in `src/Files.cmake` (git-tracked, `git add -f`)
- Header/source pairs are auto-included via `src/bff_all.cpp` (autogenerated)
- SWIG wrappers registered in `pyext/swig.i-in`
- Build: `cd ../imp/cmake-build-arm64 && ninja IMP.bff`
- Tests: `pytest test/ --ignore=test/medium_test_av.py`

## Verification

Each phase should:
1. Build cleanly (`ninja IMP.bff`)
2. Pass full test suite (801 passed, 1 failed pre-existing, 3 xfailed)
3. Show zero `%pythoncode` blocks in ported `.i` files

End state: **0 `%pythoncode` blocks** across all `.i` files.

## Risks

1. **IMP SWIG type availability in C++**: some IMP types may not have clean C++
   interfaces through SWIG. Check `../imp/IMP/` headers for availability.
2. **`RotamerEnsemble` subclassing `States`**: in C++ this is straightforward
   inheritance, but the SWIG wrapper needs `%extend` or direct wrapping.
3. **Python callables** (`radial_diffusion_map`, `read_evaluators_json`): need
   API redesign, not just a transliteration.
4. **`IMP.pmi` dependency**: `docking.i` and `sim.i` subclass
   `IMP.pmi.restraints.RestraintBase`. For JS/SWIG, these should either use the
   C++ IMP API directly or reimplement without PMI.
